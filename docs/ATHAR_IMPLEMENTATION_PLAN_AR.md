## قواعد غير قابلة للتجاوز
1. لا حذف أو تصفير أو إعادة إنشاء لأي جدول مالي أو سجل محفظة.
2. لا تغيير على أرصدة المستخدمين أو معاملات الإيداع والسحب القديمة دون مطابقة ونسخة احتياطية.
3. لا دمج إلى main أو نشر Production قبل اجتياز الاختبارات ومراجعة التغييرات.
4. كل ميزة مالية يجب أن تنفذ على الخادم وتكتب سجلاً قابلاً للتدقيق.
5. كل ما يظهر للمستخدم يجب أن يكون وظيفة حقيقية، أو يحمل وصفاً واضحاً بأنه غير متاح.
6. لا إنشاء مشروع Vercel مستقل للوحة التحكم؛ لوحة المالك جزء داخلي محمي من التطبيق.
7. لا إدخال Firebase إلى هذا المستودع دون قرار معماري منفصل؛ البنية الموجودة حالياً Vercel + Next.js + Supabase.

## تشخيص أولي مؤكد من الكود
- الصفحة الرئيسية تصدر Jo1MasterPlatform مباشرة.
- الواجهة تحتوي فيديو تجريبياً ثابتاً من Google sample video.
- عداد الإعجاب ورصيد المحفظة وبعض أرقام التفاعل محفوظة في React state أو قيم ثابتة.
- يظهر رقم هاتف داخل واجهة الشحن ويجب نقله إلى إعداد آمن وعدم عرضه إلا إذا كان مطلوباً ومصرحاً به.
- صفحة Gemini تحتوي نصاً تعريفياً وحقول إدخال دون دليل في هذا الملف على تكامل فعلي.
- شاشة اللعبة تعرض تنبيهاً بدلاً من تشغيل لعبة.
- توجد API routes في apps/mrjoo للمحفظة والهدايا والبث والتغذية؛ يجب مراجعة توافقها مع مخطط قاعدة البيانات الفعلي قبل إعادة استخدامها.
- يوجد مسار سحب يخصم المبلغ قبل إنشاء طلب السحب ثم يحاول إرجاعه عند فشل الإدخال؛ يلزم استبداله بمعاملة ذرية بعد اختبار القيود الحالية.
- كود إرسال الهدايا يعتمد RPC باسم send_gift؛ يجب فحص ملكية الوظيفة، وصلاحيات تنفيذها، ومنع تزوير هوية المرسل/المستقبل.
- تغذية الفيديو الحالية تسمح بطلب feed دون مصادقة وفق إعداد المسار؛ يجب مطابقتها مع شرط حجب المنصة عن الزوار.

## مراحل التنفيذ

### المرحلة 0 — حماية نقطة الرجوع
- إنشاء هذا الفرع من main.
- توثيق commit الإنتاج الحالي.
- جرد ملفات التطبيق والخدمات والمتغيرات دون كشف قيم الأسرار.
- مراجعة schema والسياسات والصلاحيات وسجلات المالية.
- إعداد خطة النسخ الاحتياطي والاستعادة قبل أي DDL أو ترحيل.

### المرحلة 1 — الدخول والخصوصية
- بوابة دخول حقيقية على مستوى الخادم/المسارات، لا مجرد إخفاء عناصر الواجهة.
- حجب feed والملفات الشخصية والبحث والبث عن غير المسجلين وفق سياسة المنتج.
- جلسات آمنة، وإعادة توجيه صحيحة، ورسائل أخطاء واضحة.
- إزالة بيانات الأشخاص والأرقام والأرصدة التجريبية من الواجهة.
- عدم السماح للمستخدم بتعديل أعمدة الرصيد أو الإدارة أو حالة الحظر.

### المرحلة 2 — واجهة وهوية اترك أثر
- تحويل العلامة والنسخ والنصوص إلى «اترك أثر طيب».
- تصميم تجربة فيديو عمودية أصلية.
- إتاحة التحميل والتشغيل والتبديل دون أرقام وهمية.
- ربط التفاعلات بقاعدة البيانات وواجهات API.

### المرحلة 3 — الفيديو والمجتمع
- رفع الفيديو وتخزينه ومعالجته.
- feed وتوصيات أولية قابلة للقياس.
- likes/comments/follows/saves/shares.
- ملفات شخصية ومراسلات وإشعارات وحظر وإبلاغ.

### المرحلة 4 — البث المباشر
- LiveKit من خلال إعدادات خادم فقط.
- توكنات قصيرة العمر ومحددة الدور والغرفة.
- إنشاء/إنهاء الجلسات وإدارة المشاركين.
- دردشة ومشرفون وبلاغات.
- اختبارات اتصال وأجهزة وأحمال.

### المرحلة 5 — الهدايا والدفتر المالي
- اعتماد تعريف صافي قيمة الهدية.
- فصل العملات المدفوعة والمجانية.
- دفتر أستاذ append-only ومفاتيح idempotency.
- توزيع حصة المذيع والمنصة وصندوق الأثر في معاملة ذرية واحدة.
- طلبات سحب بحالة pending/approved/paid/rejected مع حجز المبلغ وعدم خصمه نهائياً قبل التسوية.
- مطابقة الإيداعات والإيصالات وحماية التكرار.

### المرحلة 6 — الأثر الإنساني
- حالات ومبادرات مع تحقق وموافقة.
- صندوق منفصل ومحاسبة مستقلة.
- مساهمات وتخصيصات وصرف وإثباتات.
- صفحة أثر شخصية وتحديثات قابلة للمراجعة.
- حماية بيانات المستفيد والتواصل بموافقته.

### المرحلة 7 — لوحة المالك والتشغيل
- لوحة داخل التطبيق بصلاحية server-side.
- إدارة المستخدمين والمحتوى والبث والبلاغات.
- مراجعة الإيداعات والسحوبات والحالات.
- تقارير مالية وسجل تدقيق.
- لا مفاتيح سرية في العميل.

### المرحلة 8 — الاختبار والإطلاق
- اختبارات وحدة وتكامل وE2E.
- اختبار صلاحيات RLS وAPI.
- اختبار منع تكرار الهدايا والسحب.
- اختبار استعادة النسخ الاحتياطية.
- اختبار الضغط للفيديو والبث.
- إطلاق تجريبي محدود ثم توسيع تدريجي.

## معايير القبول
- الزائر غير المسجل لا يستطيع قراءة محتوى المنصة من الواجهة أو API.
- لا يوجد رصيد أو عداد أو تفاعل تجريبي ظاهر للمستخدم.
- كل فيديو وتفاعل وبث محفوظ ومملوك لصاحبه.
- لا يمكن تزوير رصيد أو مستحقات من المتصفح.
- كل هدية تخصم وتوزع مرة واحدة فقط.
- كل مساهمة أثر لها سجل وإثبات تنفيذ.
- لا يتم الإطلاق قبل اجتياز مراجعة الأمن والخصوصية والاختبارات.

حالة المشروع: ACTIVE_HEALTHY

## المشكلات التي عولجت

قبل التعديل، كانت صلاحيات `anon` و`authenticated` واسعة على جداول مالية وملفات المستخدمين. كما كانت سياسة تحديث `profiles` تمنع تغيير بعض الحقول القديمة، لكنها لم تكن تمنع تعديل أعمدة `paid_coins` و`bonus_coins` و`cash_egp` و`points` على مستوى صلاحيات الأعمدة.

ولم يكن هناك Trigger ينشئ صف ملف شخصي تلقائياً عند تسجيل مستخدم جديد.

## التغييرات المنفذة مباشرة على قاعدة البيانات

1. سحب كل صلاحيات العميل من `PUBLIC` و`anon` و`authenticated` على:
   - `profiles`
   - `ledger`
   - `deposits`
   - `withdrawals`
   - `gift_sends`
2. منح `authenticated` صلاحية القراءة فقط على هذه الجداول، وتبقى الصفوف محكومة بسياسات RLS الموجودة.
3. منح `authenticated` تحديث حقول الملف العامة فقط في `profiles`: `username`, `bio`, `avatar_url`.
4. سحب صلاحية `TRUNCATE` من `PUBLIC` و`anon` و`authenticated` على جميع جداول schema `public`.
5. إنشاء schema داخلية `private` ودالة Trigger آمنة باسم `private.handle_new_auth_user()`، تنشئ صف ملف شخصي عند إضافة مستخدم جديد إلى `auth.users`. لا تمنح الدالة صلاحية تنفيذ لأدوار API العامة، وتستخدم `search_path = pg_catalog` مع تأهيل جدول `public.profiles` بالكامل.

## التحقق بعد التنفيذ

- `anon`: لا يستطيع قراءة `profiles` ولا تحديث أعمدة الملف أو الرصيد.
- `authenticated`: يستطيع قراءة الملف وفق RLS، وتحديث `username` وحقول الملف المسموح بها فقط.
- `authenticated`: لا يستطيع تحديث `cash_egp` أو `paid_coins`.
- لا يستطيع `anon` أو `authenticated` إدخال قيود مباشرة في `ledger`.
- لا يستطيع العميل تحديث `deposits` أو حذف `withdrawals`.
- لا يستطيع العميل تنفيذ `TRUNCATE` على `ledger`.
- تم اختبار Trigger داخل معاملة مؤقتة: أنشأ الملف الشخصي كما هو متوقع، ثم تم عمل rollback للاختبار؛ لم يبق حساب تجريبي.
- أعداد الصفوف بقيت كما هي: profiles=1، ledger=3، deposits=0، withdrawals=0، gift_sends=0، test_users=0.

## ملاحظات أمان ما زالت مفتوحة

1. فحص Supabase Advisor ما زال يرصد 11 دالة `SECURITY DEFINER` قابلة للتنفيذ من `authenticated`. تمت مراجعة تعريفاتها: دوال الإدارة تتحقق من `is_admin()`، ودوال الطلبات والهدايا والتحصيل تتحقق من `auth.uid()`، لكن يلزم اختبار صلاحيات كل دالة عملياً واختبار محاولات IDOR قبل اعتمادها نهائياً.
2. الجداول `pool` و`trade_accounts` و`video_views` لديها RLS دون سياسات؛ يجب مراجعة صلاحياتها واحتياج التطبيق قبل إضافة سياسات أو منح.
3. حماية كلمات المرور المسرّبة في Supabase Auth غير مفعلة.
4. توجد ملاحظات أداء حول استدعاء `auth.uid()` داخل السياسات لكل صف؛ تعالج بعد اختبارات الصلاحيات والأداء.
5. يلزم اختبار Google OAuth فعلياً والتحقق من إعداد Google Provider وRedirect URLs قبل إعلان بوابة الدخول جاهزة.
